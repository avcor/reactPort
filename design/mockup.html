01 — FLUTTER INTEGRATION & CI/CD

Embedding Flutter in a Native Android App—Zero Cold-Start Cost

Access Management screens arrived from a separate Flutter team. The mandate: integrate them into our existing Android app without impacting cold start time, support 3 build flavors (debug / qa / release), and don’t blow up CI build times. What sounds like a routine library integration turned into a full engine lifecycle and CI pipeline problem.

Problem
Flutter engine needs ~4s to initialize cold. Each build flavor required its own AAR artifact, meaning the CI pipeline was compiling Flutter 3× per build cycle, pushing total time to 90 minutes. Integrating late also meant user tokens and auth details needed to be passed across a native-to-Flutter boundary.
Solution
Pre-warmed the Flutter engine on a background thread during Home Page load. Built a state manager (loading → ready → error) to gate navigation. Passed tokens and user details via platform channels. Pre-built flavor-specific AAR artifacts and published as an internal library so CI just pulls it — no recompile.
Impact
Screen display time: 4s → negligible. CI build + deploy to Firebase App Distribution: 90 min → 18 min. Zero cold-start regression. Works seamlessly across all 3 flavors. Developers iterate faster; QA no longer blocked by CI waits.

02 — ANTI-SPOOFING ATTENDANCE

Liveness Detection to End Proxy Attendance

Faculty were marking attendance by logging into other accounts and scanning printed photographs — completely bypassing physical campus presence. I identified the problem, built the solution case (PUC), presented it to stakeholders, and shipped it end-to-end using ML Kit with randomized challenge-response verification.

ML Kit Face Detection Liveness Challenges Geolocation verification Static IP check Kotlin
✓  Photo spoofing: eliminated ✓  PUC-driven delivery
0
proxy attendance possible
post-deployment
Problem
Faculty could authenticate as any user, then hold a photo up to the camera to mark attendance. No liveness signal existed. Physical campus presence was completely unverifiable.
Solution
Random head-turn challenges (2 of 4 directions), 2× blink requirement, single-person enforcement via ML Kit. Random frames captured during the flow, sent server-side for verification against saved photo, user’s geolocation, and registered static IP.
Impact
Proxy attendance via photo: fully eliminated. Challenge randomization prevents replay attacks. Stakeholder buy-in secured via PUC presentation before a single line of code was written — smooth rollout, zero rollback.

05 — MULTI-TENANT ACCOUNT SWITCH

Seamless Identity Switching for Multi-Role Campus Users

An MTech student who is also a faculty member and hostel warden had to fully log out and log back in every time they switched roles. The fix required coordinating token invalidation, async cache clearing, Room DB upload, Retrofit client recreation, and a full rollback mechanism — all as a single atomic operation.

Coroutines (synchronous async) Room DB Retrofit Token management Feature flags Atomic state transitions
✓  1-tap account switch ✓  Full rollback on failure ✓  Zero stale-data state
1-tap
account context switch
was: logout + re-login
Pipeline complexity: Upload pending Room DB data → invalidate old token → clear cache & persistent storage (made synchronous) → fetch new token → update user model globally → reinitialize Retrofit service with new credentials → refresh feature flags per account → sync new account data. Every stage has a named failure mode: sync failure, expired password, partial rollback, stale-data prevention.
Problem
Multi-role users had to fully logout and re-login to switch context — every time. Token invalidation, cache clearing, data sync, and Retrofit re-init all had to happen atomically with no stale state left behind.
Solution
Sequential async pipeline with explicit synchronization points. Made cache-clearing synchronous where required. Full rollback to previous account on any stage failure. Named error states for each failure mode with appropriate user messaging.
Impact
1-tap context switch for all multi-role users. Zero stale data after switch. Graceful, informative error states (sync failed, expired password, rollback confirmation). Feature flags correctly scoped per active account.

DOZEE ECG APP — Built from Scratch

Hospital-Grade ECG: Offline-First, Auto-Upload, PDF Generation

Designed and built the ECG Android app end-to-end for hospital deployment. Nurses scan patient QR codes, capture live ECG via Bluetooth, and the app auto-generates a PDF report. WorkManager ensures the report reaches the server — even in the background, even on unreliable hospital WiFi. If upload fails, it persists in Room DB and retries automatically until it succeeds.

Kotlin MVVM + Clean Architecture WorkManager Room DB Bluetooth (Coroutines) PDF generation QR scanning Offline-first
✓  0-to-1 app build ✓  99% BT connection ✓  70%+ test coverage ✓  −4 MB data/session
0→1
app built from scratch
medical-grade reliability
Why this is hard: Hospital WiFi is unreliable. ECG reports are legal medical documents. A silent upload failure is not acceptable. The app must guarantee delivery under any network condition, even when backgrounded. This required WorkManager + Room DB as a local queue, with retry semantics that survive app restarts, process death, and extended network outages.
Problem
Hospital WiFi is unreliable. ECG reports are critical medical records. A failed upload can’t silently disappear. The app needed guaranteed end-to-end delivery under constrained real-world conditions, including when backgrounded.
Solution
Live ECG → on-device PDF conversion → immediate WorkManager upload attempt. On failure: persist to Room DB, schedule background retry (survives process death). Multithreaded BT communication via Coroutines + MVVM state machine for 99% connection reliability.
Impact
Zero ECG reports lost to network failures. Medical-grade reliability for ICU-adjacent workflows. 2–4 MB saved per session via optimised REST + Room caching. 70%+ unit & integration test coverage established as team standard.
