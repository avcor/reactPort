Digii 
There are Digii App images.
group -1: First 3 image (Access Management Dashboard & Pass Console) are of access management and made in flutter and no other screens are made in flutter. There were problems how to embed the flutter screen to already existing app, in which we have to create channels to pass tokens and user details. Now another problem was different flavors such as release, qa, debug which needs to work with flutter screens. Then we have optimized the flutter engine startup time so that it do not affect cold start time of app. Also need to take care of starting engine before screen display as engine takes good amount of time to start, by starting it in background on Home Page, and maintaining the state of engine so that loader or error state can be shown. By warming up the engine we reduced the time to display screen from 4 sec to negligible. Two project also added an layer in CICD pipeline, which has increased the build time. Now I have to reduce time, in which I have prebuild aar file and make it as library so that Android CICD can just use as it is. This reduced significant time to build and deploy to firebase app distribution from 90 min to 18 min.  

group -2: 4 to 7 (My attendance) are of faculty attendance verification. There was a problem that faculty were logging to other accounts and marking attendance for others by scanning the photo of them. This bypassed the presence of faculty in campus. I presented solution through PUC to relevant stake holders. This verified the liveness of the person and made sure that no image was used. I used MLKit to detect faces, made user to turn head in 2 random directions (up, down, left, right), made sure that no other person is in screen and person did not changed. Askeed to blink twice and during this whole process I randomly take image of user and pass it into the api. Which verified users geolocation and static ip.  

group -3: 8 to 10 (Hostel Attendance, Hostel Report, Mark Attendance ) images is the first migration to compose. I had legacy code which had out dated java and gradle version, due to which I am unable to used latest features. I have migrated to latest java version and upgraded gradle. Made sure that project support latest kotlin version and Android SDKs. During this process I have faced many challenges, removed unsupported libraries such butterknife, changed the code which uses it across 100+ files. There are depreciated libraries which were not maintained and are not available in JetPack libraries, maven central, JitPack, JFrog. Due to which I have to download the project from github and made library out of it so that we can maintain it internally and used in our project. All this work resulted in successful migration and support for adding compose libraries and kotlin version of 2+, because of which I can use compose, flow, coroutines, retrofit (coroutine support), kotlin annotations. This resulted in reduced development time to 20% which helped to reuse the component easily, making sure i did not break the lifecycle invariant with the help coroutines. This also reduced UI testing time to 15%.   

group -4: 11 to 12 (Payments) images are of payment sections. There were problem that we were given ambiguous requirements which does not sounded good in respect to UI and UX. I communicated with different teams to get clear requirement gave advice on what are the possibilites we can design, what can be delivered, what is good for user. After that went to design team get the resources ready and updated my team. For new design asked backend engineer to make changes in api response, so valid data can be shown at a glance. On top of that made sure that we reduced multiple api calls when user comes back from other screen by calling the relevant api only. Made multiple parallel apis call at same time to reduced the data loading time. All this work resulted in useful screen, where student can view his financial status at a glance.

group -5: 13 to 15 (Add Account) images are of multi switch -tenant account. A product problem came where a Mtech person can be student, facult, or other staff member such as hostel warden. To do his job on app he needs to switch account by logging out and then logging in again with other account. This becomes a tedious process when he has to do multiple times. Thats why we introduced multi tenant switch so that he can change account seamlessly with out all the process. Technical problems we encountered that we have to change the token and user details. Which required api calls in some sequence so that we can discard the previous tokens and get the new ones. There many asynchronous task which were need to made synchronous, like clearing cache and persistent storage. Update the new user model and it should be available in every screen discard the existing retrofit service and make new one with new user object and token. We need to update the screens on basis account available feature flags. We need to upload the pending data to servers which was stored in roomdb before changing the account. This results in many error state such as if upload of attendance failed then we need to show attendance has not been synced please do it manually or discard the attendance and continue with process. Expired password while updating the token and options to change password. If the process failed do you want to revert the account changing process to previous valid account. If account switch is successful then we need to need to sync new data in persistent storage and next login should only take new account. We need to also prevent any mismatch of the data and user details, there could be stale data and new data at the same time which makes app's state invalid.

Group 1 - 1 to 4 chart screens where optimization happened, reduced the chart mapping time and loading time. In first iteration of the screens they were displaying chart in noticeable time about 5 sec. This was handled by some other developer then I helped him out optimizing the chart which resulted in displaying of charts under 2 sec. The problem was that in a minute there 4 data points which resulted in 9k+ data point in 8 hrs of sleep, in which we have to filter out the invalid points and smoothness the chat lines so that chart does not look like spiky one or overly smooth which does not loose information, by running algorithm and saving resulted data in watermelon db. Also I made sure that I will api call for current day, and prev day in background so that data is present even before user clicks on the screen. When user opens detail screen (charts screen) I also made sure there are no unnecessary rendering of the components by help of optimizing useEffecs and user React.memo. Charts axis needs to be adjustable to different screen size for iOS and Android, because there were scenarios when axis's labels are overlapping because of screen width. Written an algorithm where I calculate the number of axis's labels and display them. Which resulted in adjustable chart and clean UI.
